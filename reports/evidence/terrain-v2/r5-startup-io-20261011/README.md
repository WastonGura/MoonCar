# R5 启动核验工具检查（无Gazebo）

上一轮第11次仿真启动在桥接就绪核验阶段报ENODATA，物理时间0；其目录保持失败。本轮没有启动Gazebo，也没有改变车辆、控制、DDS库、容量、QoS或正式启动文件。

并发回执检查分别在Windows绑定目录和容器本地目录写入500份JSON。现有解析器完成各500次读取，未见IO异常，原ENODATA的具体来源仍未确认。1毫秒受控写入延迟是工具测试条件，不是对实际RMW时序的实测或改动。

新增测试专用守护程序生成器，要求正式guard源码SHA256精确匹配。唯一行为差异是在原10秒准备期限内，遇到ENODATA时记录异常、操作堆栈并重试；就绪标记必须在完整初始化回执与实际库、容量核验均通过后才写入。持续错误仍超时，其他IO错误及容量、版本、哈希错误立即失败。没有回退、续期或DDS参数变化；正式guard未修改。

8项专项检查通过，包括接收及运行核验的ENODATA、持续超时、权限失败、容量/版本/哈希失败、未完整回执、子进程退出、基线源码及覆盖拒绝。两次真实C++ ROS节点实际加载现有最小RMW及原Fast DDS，容量8388608字节、端口512、传输2项；均在节点真实构造与运行核验后收到SIGINT并正常返回0，输出NODE_CLOSED。

独立原安装桥接关停对照：两种配置都创建11条桥接并稳定3秒，SIGINT后原桥接返回−11、最小RMW监护程序返回245。这里只说明异常不与8MiB配置呈特异对应，不能据此确认根因，也不宣称桥接生命周期通过。它与上一轮ENODATA保持分开，所有日志保留，不回退已验收的库。

新增私有车辆验证入口，仅将测试桥接重定向到签名明确的测试guard，保持原24轮矩阵、所有配对、模型/库和停止规则。4项入口回归通过，核对选择隔离、签名拒绝、矩阵及错误链保留。原始启动异常与其造成的缺数据错误分别登记，避免主错误被次生错误覆盖。

下一车辆验证使用新容器、新目录及完整独立计数，准备完成后冻结。不得把这里的无Gazebo检查或历史车辆轮次补作物理验收，也不宣称原ENODATA原因已确认或31cm问题正式解决。原工作台保持不变。
