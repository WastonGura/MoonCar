旧正式批次 `tmp/ros_acceptance/formal-strategy-v2-voxel-precision-300s-20260918/` 在 `survey` 场景完成 18 个计划槽位后停止：16 轮有完整评价，槽位 15、18 在自主策略启动**之前**等待工作台就绪超时，没有同步原始捕获或可用 C/P/S。原始 `trials.json`、失败状态、仿真日志与 `survey-exit-code.txt=1`、`campaign-exit-code.txt=1` 全部保留，不将这两条算作策略失败或补造分数。

两个失败状态均显示传感器质量和 Nav2 服务在更新，但工作台定位报错：`map` 与 `base_footprint` 属于不连通的 TF 树。第 18 轮故障仍在现场时，`/tf2_frames` 显示工作台缓存拥有动态 `map → survey_odom` 和 `odom → base_footprint`，唯独缺少静态 `survey_odom → odom`；同一时刻，新建的 `/tf_static` 订阅者能收到 `survey_odom → odom`，而且轮速里程计、融合里程计、激光扫描与 `/clock` 都在更新。故障点是工作台 TF 订阅缓存漏接这条单次发布的静态变换。到底是哪一步 DDS 发现或订阅时序造成漏接，现有档案不能唯一确定；仿真时钟回跳告警本身也不能证明静态变换被清除。

共用启动链现于新实验开始超过 10 秒、仍无定位时，重建一次工作台 TF 订阅，以重放已有的静态变换；不改变 TF 数值、Nav2、传感器、三策略、300 秒预算、评价分母或门槛。定向测试先在旧代码失败，再于修复后通过：一项验证晚加入的订阅者能取得先前发布的静态 TF，一项验证启动时只刷新一次；完整地形测试 78 项通过。预登记的 10 次连续 Gazebo 重置与启动短验证存于 `tmp/ros_acceptance/tf-static-replay-startup-20260918/`，协议 SHA-256 为 `768d95d34e2fd937a978ccbc22edf21c2624cb9f8e58945cd69800f0665b59c9`。两处起点交替，各 5 次，10/10 次取得正确工作台位姿和就绪状态，耗时 26.4–37.5 秒，执行退出码 0；没有运行自主策略，因此没有策略成绩。这个验证支持修复有效，但不能保证将来绝无启动失败。
