## 运行基线

默认`rgbd_window`，576跟踪预算、6关键帧、96求解观测、96预热；旧主动回访和自动旧定位兜底关闭。保留原观测有效期、健康恢复和运动许可。6CPU/6GiB/1GiB shm，定位CPU0–1，Gazebo CPU2–5。受保护源码38份，沿用收尾后的最终主节点`ffe0ff44…`，新试验重新冻结清单。

不以每帧100ms、零丢帧或固定优化百分比作为本阶段门槛。关注任务能否持续完成，定位失效能否停车，恢复后能否继续，以及误差、连续空窗、延迟和资源是否随运行恶化。

## 分项验证

| 项目 | 本阶段做法 | 结论依据 |
|---|---|---|
| 区域扩展 | 原生无标柱V2，整个30×30m区域、22m活动半径，自然选点 | 实际路径范围、观测覆盖、动作与停止原因；设置为全场不等于完成全场覆盖 |
| 长时间 | 同轮配置600仿真秒，记录墙时、逐帧状态与RSS | 实际持续时间；提前中断即本项未通过，短样本不能证明内存长期稳定 |
| 明显坡面 | 原生V2另一安全平地起点，固定接近粗糙坡段，仍经产品导航和健康联锁 | 真值仅离线评分，记录真实车体倾角、到达位置、误差和安全拒绝；接近坡面不等于驶过坡面 |
| 实车 | 先完成下面接入记录，硬件到齐后只读采集，再架空轮和低速闭环 | 实际设备、标定、物理停止记录；仿真通过不代替实车测量 |

若自然扩展任务提前失败，保留该轮，不通过重复抽到成功样本来取代它。定位算法修复另开明确任务；测试中不放宽安全条件或恢复旧主动回访。全场完整覆盖仍需后续多起点或分区任务证据；本次只有一个自然起点。

## 实车接入准备记录

硬件状态由用户确认“还没齐”。Windows串口枚举本次没有返回串口设备，这只说明本机未枚举到设备，不能推断整车采购状态。没有开启电机、串口解锁或真机导航。

| 项目 | 到货后需登记/验证 | 当前状态 |
|---|---|---|
| 主机与版本 | 计算板、系统/ROS、软件版本、散热供电、CPU/内存与相机实际模式 | 待设备 |
| RGB与深度 | 实际相机型号、分辨率、内参/畸变、光学外参、单位；当前传输按相同曝光时间戳配对，两路不能拿回调时间冒充同步 | 待设备及配对检查 |
| IMU | 有效姿态四元数、角速度单位、安装轴向、相机曝光前后采样；当前订阅要求reliable QoS，需核实际驱动兼容性 | 待设备及录制 |
| TF与云台 | 实测相机到车体变换，运动云台需要同一曝光时刻的反馈TF；固定相机需给出正确固定外参 | 待安装方案 |
| 时间 | 硬件`use_sim_time=false`；图像、IMU、TF使用一致时钟，检查偏移/延迟/回跳，保留原始时间戳 | 尚无实测 |
| 定位权威 | 窗口输出一份`odom→base_footprint`及导航Odometry；禁止和轮里程计/EKF重复发布该TF | 尚未建立整车启动入口 |
| 底盘与链路 | 端口、编码器计数、轮径、有效轮距、四轮方向与速度、看门狗/串口失联停止 | 待实测 |
| 物理停车 | 独立急停、通信断连、控制进程退出，实测停止时间/距离 | 待实车验证 |

已有`hardware.launch.py`是轮式里程计台架入口，默认由轮里程计发布TF；不能把它直接与窗口主节点叠加并宣称整车已适配。本阶段不猜测标定参数、不自动修改EEPROM或解锁电机。

第一份实车记录应包含RGB、深度及两路CameraInfo、IMU、TF/TF_static、关节反馈与轮速、时钟/接收时间诊断；静止、手动缓慢平移和转向分别记录。先核时间、单位、配准和坐标，再只读跑窗口定位，最后才接运动许可。已有接线/台架步骤见[硬件交接](hardware_handoff.md)，具体参数缺口见[参数待补清单](hardware_parameter_gaps.md)。
