# MoonCar 仿真性能核查与无界面批处理验证

## 结论

当前 Gazebo、深度相机、激光、SLAM、Nav2 和评价链主要在 CPU 上运行。现有容器使用 `runc`、限制 4 个 CPU 核、没有 GPU 设备请求，并设置 `LIBGL_ALWAYS_SOFTWARE=1`。主机 RTX 4060 可被 Docker 的计算运行时识别，但临时 `--gpus all` 检查仍由 Mesa `llvmpipe` 提供 EGL/OpenGL，因此不能把现有实验直接切到硬件图形渲染。

批量 runner 已改为关闭 Gazebo GUI 和异步现场截图，交互工作台仍默认显示 GUI。三种策略、物理场景、Nav2、传感器、记录器、评价指标和阈值均未改变。

## 实测

- 原 90 仿真秒批次的 4 个完整采集耗时：403.79、403.48、301.42、336.39 秒。
- 原运行观测峰值约 413% CPU、1.94 GiB 内存；其中 `gz sim -g` 单独约占 1.79 个 CPU 核。
- 15 仿真秒无界面样例总墙钟时间 82.9 秒；同步采集阶段 25.59 秒，记录 20 个原始深度帧。
- 无界面运行观测约 364% CPU、1.08 GiB 内存，进程列表不再包含 `gz sim -g`。
- 停止后容器约 2.25% CPU、495 MiB 内存。
- 样例完整生成评价：`C≈6.94%`、`P=100%`、`S≈6.94`，因覆盖不足未通过。该数值只用于验证无界面链路，不比较策略。

## 决定

无界面模式能明显减少内存和 GUI 额外负担，但没有把核心仿真迁移到 GPU，也不足以让原 54 轮批次变得轻量。原批次保持中止，不直接恢复。

下一轮先采用最多 6 轮、每轮 30 仿真秒的同条件管线试验，预计总墙钟约 12 至 25 分钟。它只检查三种策略都能在新评分链下稳定留下可评价证据，不用于统计优劣。6 轮完成后才依据运行稳定性冻结论文对照规模；不得依据策略成绩决定是否扩展。

没有安装依赖、修改驱动、网络或 Docker 全局设置。
