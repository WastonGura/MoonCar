# V2旁路覆盖、迟到变差的原因核查

2026-10-23，Asia/Tokyo。只读取已闭合的cd2f、ffe3两轮数据及源码；没有新世界、回放、性能实验或产品代码改动，默认定位、回访和资源保持。

**直接原因已分清：启动消息突发与IMU就绪等待造成一段空窗；运行中的长耗时帧与串行排队造成其余覆盖及迟到。移除关键帧重复计算只缓解了其中一部分。** 现有证据不能继续唯一归因到DDS、Python回调、GIL或系统CPU调度。

按各轮实际就绪屏障、driver动作起止分类，云台序列包含各云台动作之间的停顿；全窗保留，不以分段替代原整体验收。

|---|---:|---:|

新增5次净额为启动+3、云台+6、其余−4。本轮21次覆盖按受害曝光收到时的worker分类为就绪等待3、关键帧9、普通query9。7次成功输出迟到中6次处在云台序列，1次处在转向完成与最终等待之间；平移、转向动作窗内无成功输出迟到。这是事件分布变化，不能据此删掉启动或扫描失败。

## 2. 最大0.646仿真秒空窗的完整因果链

成功的2.7秒曝光在2.748sim交付，下一成功3.2秒曝光在3.394sim交付。中间发生：

1. 2.7、2.8、2.9秒图像成批到达，后两次接收间隔仅17.6、16.9毫秒。上轮全窗无小于50毫秒的配对到达间隔，本轮仅这两次。2.7处理期间，尚未处理的2.8被2.9替换。
2. 2.9取出后，等待其曝光时刻的合格IMU前后样本，0.505秒墙时后超时。等待占用唯一worker，3.0、3.1随后被覆盖。
3. 3.2恢复成功输出。此段在9.834sim就绪屏障之前；交付空窗0.646sim，其中真正不新鲜部分为0.394sim，不能混用。

只读原袋约1.3墙秒的小窗口：82条IMU、41条/clock，不解图像、不回放。可靠录包中IMU 2.65–3.13秒以10毫秒连续覆盖，包含2.89、2.90、2.91；到达记录也早于旁路开始等待。**因此不能归因于发布端没有这段IMU数据。** 旁路等待期间IMU计数121→162持续增长，500条历史缓存未满，且未记录invalid/missing-TF/nonincreasing计数；不是整个IMU处理停止或500条缓存淘汰。

更具体的线索是：该段IMU也突发交付；旁路使用sensor-data best-effort浅队列，独立observer确实漏掉2.85–2.90秒。支持旁路订阅/回调路径遗漏历史括号的判断，但旁路未记录每条IMU header，**不能把observer的精确缺口直接当作旁路缺口**。/clock另有约348毫秒交付停顿；imu_at只使用header，clock停顿本身不能单独解释括号失败。DDS、executor、主机调度三者尚无法唯一细分。已漏历史样本不能靠继续收到更晚IMU补齐。

## 3. 七次迟到不是同一种机制

| 曝光sim秒 | 排队/交接 ms | 自身处理 ms | 端到端 ms |
|---|---:|---:|---:|
| 11.3 query | 254.0 | 378.2 | 632.3 |
| 12.4 query | 229.7 | 317.3 | 547.0 |
| 14.2 KF | 208.3 | 309.6 | 517.9 |
| 15.3 query | 246.7 | 335.5 | 582.1 |
| 15.7 KF | 0.3 | 648.2 | 648.5 |
| 16.2 KF | 142.4 | 381.7 | 524.1 |
| 41.3 KF | 0.2 | 508.0 | 508.2 |

其中5个有明显等待的事件由前序任务阻塞后，再叠加自身处理超过0.5秒；另外15.7和41.3几乎没有排队，单帧自身已超门。单worker和只保留最新待处理帧的结构，将长等待/长处理转化为后续覆盖。单纯延长队列不能使结果及时。

记录的queue_wait从收到图像到worker开始，含图像capture、配对、offer和交接，不是纯mailbox等待。自身处理含调度墙时，不能直接称CPU计算时间。front计时后、backend计时前还包括选点/观测转换/Frame构造；7个迟到中该类未细分处理余量为6.1–27.9毫秒。finished之后仍有plain转换、JSON写出/flush和processed事件，可能延后下次取件。上述路径均原已存在。

## 4. 为什么缓存变快，整体仍变差

| 墙时指标 | 上轮 | 本轮 |
|---|---:|---:|
| 缓存构建P95 | 86.6ms | 56.1ms |
| 视觉处理attempt P95 | 164.8ms | 188.9ms |
| 普通query后端P95 | 54.5ms | 79.2ms |
| KF后端扣除各自cache的平均耗时 | 77.8ms | 100.6ms |

固定输入离线对照已把两次签名、交接和复制计入，KF含cache P95仍下降25.4%；在线cache本身也下降。普通query没有调用新签名，不能把所有变长都直接归因于签名。冻结数组复制也是保留的原流程。

两轮在线输入/初始化不同：KF状态维度均值594.6→621.4，信息矩阵非零项P95约144715→175489；普通query缓存列数并未整体增加。输入工作量和共享调度并非严格相同，单轮墙时差值不能证明某个新函数造成整体退化。**目前确定的是缓存节省没有转化为整条链的足够余量；尚不确定的是其他阶段增加的墙时中，计算和调度分别占多少。** 不能据此宣布定位数学回归，也不能宣布实时性已修复。

下一次若继续定位原因，最小测量应覆盖：旁路IMU实际header/接收序列与等待时的前后样本；真实offer/take；签名、选点/观测构造、求解、冻结复制、完成后写出各阶段墙时与线程CPU。现有日志不足以用删检查、放宽门或扩大队列作有根据的修复。本次仅记录此测量边界，未实施或新增实验。
