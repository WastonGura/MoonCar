# 整场退出与坡面断链：原因核查

2026-11-02，按用户“找原因”只分析两轮既有记录。没有改产品源、安全门、回访或默认配置，没有新建仿真世界、派发运动或重跑整轮测试。容器仅用于只读提取与离线前端重放，分析结束已停止。

## 整场退出：派发时的临时定位拒绝没有接入恢复流程

原任务`experiment-61097abbfa79`的“等待导航结束及转向服务就绪”是一个合并错误信息，条件来自`ExperimentMotion.turn`：当前动作active、综合ready为false、或spin服务不可用，任一项都会抛同一个`ValueError`。

关键时间线：

| 仿真秒 | 任务／运动状态 | ready | 定位健康 | spin服务 |
|---:|---|---|---|---|
| 381.950–382.079 | 正在执行spin | true | healthy | 可用 |
| 382.260–382.526 | 原spin已取消，等待定位恢复 | false | recovering | 可用 |
| 382.696 | 恢复，运动inactive/cancelled，准备继续 | true | healthy | 可用 |
| 382.706停止诊断 | pose读取被拒绝，任务fault | false | observation_stale | 可用 |
| 383.163 | 任务已退出，定位再次恢复 | true | healthy | 可用 |

停止诊断的最后接受曝光是382.4秒，诊断时钟382.706秒，观测年龄约0.306秒，越过原0.3秒有效期。综合ready依赖pose有效性，因此临时定位拒绝足以让turn的综合ready检查失败，即使没有旧动作在执行且spin服务可用。

`AutonomousSurvey.execute`会处理“动作返回false且期间新增暂停记录”的重试；但`_execute_once`把转向派发时的`ValueError`直接重新抛出，`execute`没有把该异常分类为临时定位变化。外层`run`捕获后直接结束整个任务。

所以可复现的中断路径是：**健康检查通过 → 到动作派发时观测刚过期 → 综合ready拒绝 → 抛通用异常 → 未进入原暂停恢复 → 整轮fault**。此前对`healthy()`内部第二个快照的修复，没有覆盖健康检查返回后到实际派发之间的时效变化。

核查使用原`turn`方法AST及原`execute`，驱动同样“前两次ready、派发时失效”的记录条件：motion inactive、spin可用仍得到完全相同异常，且没有创建任何暂停事件。没有实例化ROS节点或发运动。轮询日志没有记录Python条件求值的每个瞬间，重放说明源码中与记录一致且足以造成该失败的路径，不把它包装成物理导航重跑。

修复方向应是：动作派发端明确区分临时定位拒绝，并在保持停车/撤销许可的前提下接回已有恢复逻辑；不能只靠通用“服务未就绪”字符串终止任务，也不需要放宽0.3秒保护。

## 坡面断链：空间合格条件同时控制了旧点身份存续

原任务`experiment-d717ce14cb41`首个持续失败曝光为57.3秒。按原在线关键帧提交/安装顺序，用相同实测RGB、深度、内参、IMU和相机TF重放前端。可提取676帧的完整前端诊断与原记录676/676一致，包含第一失败及后续不可恢复状态；没有使用真值、旧位姿、轮速或已知地形给前端造关联。

第一失败帧的逐级结果：

| 阶段 | 数量／结果 |
|---|---:|
| 进入光流的旧点 | 125，全部保留，包含39受保护点 |
| 前后向光流验证 | 33点 |
| 光度检查 | 33点 |
| 有效连续深度 | 33点 |
| 三维几何一致性 | 33点 |
| 空间分布 | 当前和上一帧均只占5个图像分区，原门要求至少6个 |
| 其他空间条件 | 图像跨度、米制支撑特征值及有效ROI均通过 |
| `_track`最终返回 | `None`，整批旧身份没有传给当前帧 |
| ORB补点 | 63个新身份，选43个；空间合格但与旧窗口连接0个 |

具体空间量：当前跨度约[0.534,0.321]、上一帧[0.525,0.311]，均达到原0.30要求；第二米制特征值约0.028m²，超过原0.0025及相对比例条件。唯一失败项为图像分区占用5＜6。诊断通过只包裹原`_spatial_support`返回值进行记录，未修改其布尔结果或任何门槛，重放输出仍与原记录一致。

`TrackFrontend._track`一旦空间检查失败就返回None；`process`随后将当前特征表全部换成新检测点及新ID，覆盖`self.previous`。现有在线流程只靠相邻帧传播ID，没有执行旧关键帧描述子重关联。57.4秒以后图像跟踪本身已恢复（如47、57、54个点继续跟踪），但它跟踪的是新ID，与已提交地图连接始终为0，因此查询/关键帧都不合格，最后恢复超时。

这次不是跟踪预算把受保护点裁掉：125/125和39/39都保留；不是后台崩溃/过期缓存：版本128已在57.1秒构建成功，首失败时缓存仅0.2秒、无后台fault。关键帧提前更新本轮33次实际运行，但无法修复一次整批ID重置后的历史连接。

因此持续失败的直接机制是：**可跟踪点暂时收缩 → 单帧空间检查不合格 → 丢掉整批旧身份 → 新点不能认回旧窗口 → 长时间断链**。空间检查是否允许发布位姿与是否应保留已经验证的轨迹身份，目前耦合在同一个返回路径上。

本轮已查清导致永久断开的具体代码路径；为何进入该帧时光流有效点从125降到33，涉及图像运动/纹理/观测变化，尚未做单因素归因。不能将3.47°宣布为车辆通用坡度极限，也不能仅凭本次门槛失败认定应把6格改成5格。

修复方向应先区分轨迹维护与位姿发布资格：保留经真实光流/光度/深度/几何验证的身份，原位姿质量门继续有效；若已失去足够地图连接，还需要受验证的旧关键帧重关联，不能伪造ID或重置坐标/协方差。此处只给方向，没有实施修改。
