# RGBD 前台跟踪与后台关键帧优化：下一步开发方案

2026-10-29，Asia/Tokyo。独立双线程离线原型已实现并通过本轮离线筛查；实际实现、首版内存失败、修复和验证见 [执行报告](../reports/ASYNC_RGBD_PROTOTYPE_20261029.md)。2026-10-30又完成原始消息完整链路AB/BA，确认前后改善、严格100ms墙时预算未达标，见 [完整链路报告](../reports/ASYNC_FULL_CHAIN_20261030.md)。下文保留实施前方案及后续门槛，尚未接入工作台或默认定位。

## 目标与依据

保留现有测量、跟踪和滑动窗口方法，评估能否通过执行方式改变避免关键帧阻塞普通帧。上一轮5分钟筛查中，普通帧服务平均61.85ms/P95 89.04ms，关键帧101.23ms/P95 126.04ms；3000帧全部输出，但100ms截止违约16.57%，不是稳定10Hz。这些是准备完毕输入的人工往返重复筛查，未覆盖在线ROS/仿真并发或长期精度。

先做独立离线原型；不替换默认、不接工作台、不动回访、不更换特征/定位模型。通过原型门槛后，再单独安排完整链路和V2验证。

## 为什么先做双线程

当前 `QueryCache` 含SuperLU分解、RLock、MappingProxyType和按地标ID记忆的逆矩阵列；不是可直接pickle的跨进程消息。直接采用进程并发送整个缓存不可行；若在前台重建分解，会重新引入耗时。现有冻结后验的数据拥有独立数组，但缓存内部memo仍可变，也不能笼统称为完全无状态对象。

第一版采用同一进程的两个执行线程，共享已提交快照引用：前台负责图像跟踪与普通帧查询，后台独占估计器并执行关键帧求解/冻结。只在交换任务/结果引用时持短锁；不在求解、采样或查询期间持发布锁。每个缓存版本仅由前台执行查询并维护memo，后台不同时查询同一缓存。后台只在自己的估计器上构造新版本，不修改正在查询的旧版本。

双线程并不保证提速，GIL和原生线程争用必须实测；即使调度分开，CPU总工作量也没有凭空减少。第一版的用途是验证状态协议及在固定资源下的真实收益。若争用吃掉收益，停止该实现，不继续堆线程；后续再评估传输数值后验的进程方案或调整处理频率，单列开发和数值验证。

## 数据流与所有权

前台每帧完成 TrackFrontend.process、基于当前已确认窗口的选点、构造Frame和当前曝光位姿查询。到关键帧时，将不超过96个观测的独立Frame及提交关联信息交给后台；不把整张RGB/深度图或前台可变特征字典交给后台。

后台顺序执行 add_frame_with_posterior、freeze_query_cache，成功后返回一个整体结果：cache_version、gauge、关键帧曝光时间、窗口关键帧时间戳/已提交地标ID、只读观测与后验快照、提交状态。前台只在帧处理边界接收完整结果，同时更新选点依据和缓存版本。不能先把候选关键帧标成已提交，再等待后台是否成功。

前台持有的当前跟踪字典、轨迹年龄和上一帧始终由前台独占；后台估计器和候选状态由后台独占。界定观测所有权并核对拷贝后的数据，防止候选Frame在提交前被前台后续帧改写。

## 必须先解决的语义

1. **初始化**：第一个有效关键帧完成之前没有可查询缓存，明确记录未初始化和无输出；不隐藏启动耗时。
2. **版本与选点**：同一帧的选点、查询、已提交ID和gauge来自同一已确认版本。后台完成的新结果到下一帧边界才切换。
3. **曝光与重复观测**：普通查询使用不含本帧观测、且关键帧时间不晚于当前曝光的缓存。不能在刚包含本帧的后验上再次加入同一观测；同曝光提交结果需独立处理，不能重复计算。
4. **关键帧当前输出**：后台慢任务完成后返回的是历史曝光结果，不能换上“当前时间”当成新定位。前台对该曝光的查询、历史提交结果和下次曝光的查询各自保留真实时间戳及来源。
5. **提交事务**：求解与缓存构建全部成功才能推进已提交状态。冻结失败时不得留下“后台估计器已推进、前台版本未推进”的隐性分叉；在后台用明确检查点/事务恢复已提交状态。不要靠无界深拷贝维持事务。
6. **失败与旧缓存**：旧版本仅在其自身观测支持、版本一致性和预设年龄范围内使用，并明确标出更新失败。不能静默沿用旧缓存、忽略失败或沿用失败候选的ID。
7. **刷新节奏**：分别记录last_requested与last_committed；不能因任务尚未完成就每帧重复提交同一关键帧候选。
8. **时效**：缓存年龄上限在实验前按关键帧周期与允许延迟预算冻结；输出曝光年龄与现有新鲜度要求保持。不能通过扩大年龄阈值把旧定位算成新结果。

后台最多1个运行任务、1个待处理任务，待处理任务被覆盖必须记录。结果槽最多1个待接收结果；前台不保留所有历史版本。每个候选携带起始提交版本，若覆盖/失败改变其依赖关系，应重新校验或明确拒绝。仅保留当前查询需要的旧引用和最新已提交快照，完成使用即释放。

## 开发顺序

### 第一步：单独实现任务、结果和提交协议

新增独立 `scripts/offline_rgbd_window/async_processor.py`，保留同步 `ShadowProcessor` 作为基准；前端提供明确的已提交窗口元数据入口，避免后台直接调用会修改前端特征字典的commit。协议测试先覆盖版本过期、乱序完成、候选覆盖、首次启动、冻结失败回滚、快照切换、关闭中任务及旧版本内存释放。可使用可控的后台延迟/失败注入，不启动ROS。

特别验证：后台故意停顿时，前台不阻塞等后台完成；但超过缓存有效性/观测支持时须真实无输出并记因。线程异常必须可观察，关闭时有界等待并释放资源，不能遗留后台工作。

### 第二步：固定126帧的确定性回放

先通过可控完成时刻、固定候选提交顺序的协议回放建立数值正确性。异步提交时序不同会改变窗口历史，不能要求它与旧同步版本每帧天然相同。应比较同一已提交版本、同一当前Frame、同一选点时的同步参考查询，核对位置、完整条件协方差及接受/拒绝；再单列真实异步与旧同步历史差异。

冻结输入、候选生成规则、资源总预算、评分起止与阈值。按源计划时刻计时，包含等待、数据拷贝、交接、发布和所有失败。初始无输出、观测断链、后台任务被覆盖和迟到均计入共同分母，不只统计成功快帧。

### 第三步：真实调度下的持续运行

在同一资源总预算下做同步/异步配对，不通过额外CPU或放慢输入伪装改善。记录前台服务、后台服务、队列等待、任务/缓存年龄、线程CPU、进程CPU、数据交接、RSS、队列及窗口大小。

先复用5分钟、3000帧人工往返视图筛查，只有它通过才做更长运行。判据保留100ms截止违约<1%、服务P95<100ms、窗口/队列有界、稳定RSS无持续增长；另逐项报告初始化和运行中无输出，不通过删帧改善耗时。阶段一需留出传感器准备/写出余量，不能把准备帧刚好100ms当作线上已通过。

质量阈值在运行前冻结：同快照参考查询数值一致，真实异步的观测支持/连续性及可用精度指标不得因跳过检查或减少有效输出而改善表面延迟。真值仅用于回放后的评估，绝不能进入前台/后台计算。不确定性仍是条件性估计，不因并行通过而宣称校准完成。

### 第四步：通过后才做完整链路与V2

先沿用原始消息定时回放，计源计划发布→真实写出交付，全分母统计收不到、覆盖、就绪失败、无解和迟到；该步骤通过后才在V2旁路验证平移/转向及长期运行。默认和回访保持原状。

## 继续与停止的判断

第一版的成功条件是有界异步执行在同预算下显著降低前台阻塞，同时保持有效观测与质量。若前台本身仍经常超预算，或失去新快照后持续断链、资源竞争无收益，即停止这一原型，保留证据，不继续叠加微调。

到那时再选择调整处理频率、将测量前端迁至原生实现，或重选定位路线。首先改变执行方式并不是保证算法一定能长期可用；它是当前成本较小、能直接检验同步阻塞假设的下一步。

工作量为中等规模改造，主要风险是提交与快照一致性，不是增加线程API。先交付可独立验证、也可独立淘汰的离线原型，避免一次改动算法、调度和工作台后失去比较依据。
