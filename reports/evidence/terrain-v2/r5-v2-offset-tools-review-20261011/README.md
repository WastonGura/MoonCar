## 剩下两个核心实现缺口

### 执行入口仍未连接真实调度

`run_diagnosis_campaign.py` 的 `--run-round ... --authorized` 分支仅打印开始执行，随后结束。源码没有调用仿真、单轮脚本或子进程。`dry_run_check` 的 `executable_command` 仅是字符串，写的是 Humble、`mooncar-r5-workbench` 以及未映射的 Windows 路径，而约定是独立 Jazzy 容器及保留原工作台。

即便手动执行该字符串，也只有连续 `gz sim -r`，没有 ROS 发布器、安全中继、桥接、真实命令确认及 `paused_steps`。它不能完成计划中的 5/20/3 秒运动试验。无需启动仿真即可从代码确认这个缺口。

应接入已有 `scripts/check_r5_turn_gate_validation.py` / `scripts/check_r5_turn_slip_round.py` 调用链及原 `r5_step_schedule.py`，以测试专用输入加载已核验的副本，保留传感器和输入资格。不能直接重跑旧完整矩阵，也不能把打印命令当成实际完成。

### 原因分析需要的事件未完整保存

原轮次被识别为 4244 条关键事件，但结果只保存 `critical_events[:10]`，实际为 5201–5210 步；**17019 的目标突变没有保存**。`GRID_EDGES` 定义了邻边，但并未被用于求交，也没有恢复与基线的比较或逐事件冲量核对。全程冲量不能替代局部异常与接缝的关联。

CLI 的 `write_text` 也没有防覆盖。本次只对本复核目录里新建的人工 marker 文件作覆盖探针，它被覆盖且退出码为 0。没有修改旧证据，但这说明“拒绝覆盖原证据”的声明不成立。

评估器仍对缺少/解析失败的阶段回执静默回退，并依赖固定 1 ms 及连续行索引；应在实际诊断模式要求真实边界和逐步网格合格。人工夹具可保留明确的测试模式，不能使正式分析静默接受缺回执。
